What it does

Three things, and only three.

A small daemon on your machine plus a web app. It doesn't run your agents, wrap them, or change what they do. It watches the transcripts they already write, and gives you a second place to answer when they stop and ask.

How it works

A daemon, a relay, and a key that never leaves you.

Four parts. The relay in the middle is deliberately blind — it moves ciphertext and knows which device it came from, and nothing else. Your account key lives in your browser and in ~/.tether/identity.json on paired machines, and travels only inside pairing codes you copy yourself.

Encrypts and forwards

Normalises each line into render-ready events, encrypts them with a per-session key, and pushes them over a WebSocket. Zero dependencies. Runs as a launchd / systemd service.

holds: account key · device key
Relay

Stores ciphertext, routes it

Authenticates daemons by Ed25519 signature and browsers by token, stores encrypted events in SQLite, fans them out to your devices. It cannot read a single message.

sees: ciphertext · device id · session id · timestamps

Decrypts, renders, answers

Derives the session key from your account secret, decrypts in the page, and shows the live transcript. Your decision goes back the same way: sealed, routed, delivered.

The one rule

Tether never changes what an agent does. It only adds a second place to answer.

Every agent's own permission logic — auto mode, allow rules, deny rules — runs first and untouched. Tether never invents a prompt the agent wouldn't have raised, and never holds a call the agent would have approved on its own. When the agent genuinely stops for a human, that prompt appears in your terminal and on your phone at the same time.

Honest boundary. The folder-trust dialog, login and OAuth prompts, sandbox network prompts and managed-settings approval happen outside any tool call. No hook fires for them. They're shown in the UI, but must be answered at the machine.
Interactive sessions

A terminal, Cursor, VS Code — anything you started yourself. Tether holds the PermissionRequest hook, which fires only after the CLI has decided a human must answer. The local prompt stays on screen; the card appears on your phone; first answer wins. Every tool is covered, MCP tools included.

Sessions Tether starts

A prompt or new session sent from the web UI runs headless, with no terminal to prompt at. It gets --permission-prompt-tool pointing at Tether's own MCP server, which the CLI calls only for decisions it couldn't make itself. Questions come back with their actual choices.

In a tmux pane

Where the session has a pane, Tether mirrors the real prompt from the screen and answers it as a keystroke — no hold at all. Start a session as interactive from the UI and this is what you get.

If anything fails

Every mechanism degrades to exactly what happens without Tether. Daemon down: sessions run locally and the mirror catches up. Relay down: the daemon retries with backoff. Nobody answers: the local prompt simply remains. Tether can only ever add a way to answer, never lock you out.

Install

Up in about five minutes.

One Node package for the daemon and the relay both. Node 22.5 or newer. The daemon has no dependencies; the relay has one, ws. Everything sensitive lives in ~/.tether/, mode 0600.

1

Run a relay

Locally to try it, or on a small VM to reach it from your phone. Anything that isn't localhost needs HTTPS — browsers only expose the crypto APIs on secure origins.

# laptop, to try it
npm i -g @astrakratos/tetherd
tetherd relay                        # http://127.0.0.1:8787

# a VM, behind Caddy or nginx with TLS
TETHER_DB=/var/lib/tether/relay.sqlite HOST=0.0.0.0 PORT=8787 tetherd relay
2

Create an account, pair a machine

Sign up in the browser with an email and password. The account id and encryption key are generated in the page; the relay is handed a hash to verify you and a sealed copy of the key it can never open. Then press Pair a machine and copy the code — it carries your key, and the relay only ever sees its hash.

One command pairs it, detects every agent installed, installs Tether's hooks alongside your existing ones, and starts the background service. tetherd disconnect reverses all of it and leaves other tools' hooks untouched.

What the relay can never read

  • Any transcript content — messages, tool calls, results, file contents
  • Any prompt you send, question you answer, or approval you give
  • Your account key, your password, or anything derived from them
  • Which model a session is on, its working directory, its title

What it stores, in the clear

  • Device ids, session ids, sequence numbers, timestamps — enough to route and resume
  • A hash of your password-derived auth value, and your sealed key blob
  • Approval status — pending, approved, denied, expired — never what was approved
Transport

Every payload is AES-256-GCM. Keys are derived per scope — session:<id>, prompt:<id>, approval:<id> — via HKDF-SHA256 from your account secret, so no two sessions share a key.

Identity

Machines authenticate with Ed25519 device keys by challenge–response. Browsers use per-device bearer tokens, so signing in on your phone never signs you out on your laptop, and any device can be revoked alone.

Your password

Never reaches the relay. The browser derives an auth hash (sent, to prove who you are) and a wrap key (kept) from it. The wrap key seals your account key into a blob the relay stores but cannot open. Sign-in downloads that blob and unwraps it locally.
